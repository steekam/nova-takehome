Part 1 · actors

People own and act on plans

One user table represents both teacher and curriculum-lead accounts.

Relationship counts

One teacher can own many plans. Each plan can have many versions and review records. User references identify who authored a version or made a review decision.

Auth boundary

Sessions resolve a user to a role and permission list. Lesson-plan ownership and lead review permissions are enforced by API services.

Part 2 · retrieval corpus

Documents contain searchable chunks

The chunk row carries the retrieval text and 384-dimensional embedding.

100%

Document metadata

subject and grade are free text. There is no framework/release/programme hierarchy or normalized subject/grade catalog in this implementation.

Retrieval unit

Each chunk stores its own content and BGE-small embedding. The database requires exactly 384 vector dimensions and uses cosine distance with an HNSW index.

Current target mapping

There is no curriculum_targets table. API outcome rows pair a learning-outcome document with a chunk; the chunk UUID is exposed as targetId.

Part 3 · lesson-plan content

Plan identity is separate from version content

The plan row holds owner and lifecycle status; each immutable version holds one JSON content snapshot.

100%

content · lesson-plan JSONB

Identity: title, subject, grade, learningOutcome, durationMinutes.

Teaching: objectives[], materials[], starter, activities[].

Learning check: checkForUnderstanding.

Grounding: sources[] with documentId and chunkId UUIDs.

Nested activity / source records

activity = title, description, durationMinutes.

source = documentId, chunkId.

Schema validation checks required fields and at least one activity/source. Citation IDs are JSON values, not database foreign keys.

Version rule: editing inserts a new version row; plan status and updated time change on the parent. The API returns the newest version as the plan’s content. The database does not store a current-version pointer.
Part 4 · workflow records

Reviews point to a plan, status carries state

Review history stores the lead’s decision and comment. The submitted version is not referenced directly.

100%

Database safeguards

Primary UUID keys; foreign keys connect plans, versions, reviews, users, documents, and chunks. Unique indexes enforce email and per-plan version numbers.

Audit gap in current shape

A review record references the plan only. To prove which immutable version was reviewed, add a lesson_plan_version_id foreign key to review history.

Potential next schema slice: normalized Curriculum → Grade → Subject → Target entities; resource revisions and locator/provenance; explicit plan citations; review-to-version link. These are modeling gaps to discuss, not tables in the current database.
