Part 1 · actors

Users own plans and record actions

Teacher and Curriculum Lead are roles on one user table.

100%

users

Unique email, password hash, and one role. The API derives identity and permissions from the authenticated session.

Ownership

lesson_plans.teacher_id is a foreign key to users.id. Every version records its author; every review records the acting lead.

Attribution

Source revisions and source links record the user who created or published them. Role checks stay in API guards and services.

Part 2 · curriculum catalogue

Frameworks resolve to versioned targets

Grade, subject, strands, and targets stay in a defined programme and curriculum release.

100%

Structured scope

framework → programme → offering joins a curriculum level and subject. Codes are unique inside their framework or parent record, not globally.

Revision boundary

curriculum_design_versions stores edition, revision number, origin, publication status, source revision, and optional superseded version.

Strands and outcomes

curriculum_nodes form a same-version parent tree. curriculum_target_revisions point to a node and design version; a source locator is unique within that release.

Seeded values: the schema can represent grades, stages, years, or qualifications. The demo seed uses CBC grade/programme values; it does not claim Cambridge curriculum content.
Part 3 · source library and retrieval

Immutable source revisions feed target-linked chunks

Provenance, approval, curriculum links, and vector representation are separate records.

100%

Source identity and revision

library_resources stores stable title/type/authority. library_resource_revisions stores immutable edition/content metadata, URL, checksum, status, creator, and publication time.

Target link

curriculum_source_links joins a target revision to a resource revision with role and status. The unique key is target + resource revision + role.

Retrieval and citations

lesson_plan_retrieval_candidates freezes the chunks supplied for generation. lesson_plan_version_sources stores cited chunks for each saved version; both have chunk foreign keys.

Current UI scope: browse and inspect. Seed/import paths populate source data; upload, extraction, lead approval, chunking, embedding, and publication screens are a future extension. See source ingestion design.
Part 4 · lesson plans

Plan identity is separate from immutable versions

The parent stores ownership/state. Version rows preserve content, target, author, and exact source references.

100%

content · shared JSONB contract

Target: title, subject, grade, learningOutcome, durationMinutes.

Teaching: objectives[], materials[], starter, activities[].

Learning check: checkForUnderstanding.

References: sources[] with documentId and chunkId.

Nested records and constraints

activity = title, description, durationMinutes.

source = documentId, chunkId.

Shared schema validates fields; API QA checks duration totals, target match, published source identity, and frozen candidate membership.

Version rule: every teacher edit inserts a new version. The API selects the highest version number as current; no mutable pointer can drift from version history. Plan content is JSONB, while source references also have normalized join rows for foreign-key integrity.
Part 5 · review audit and invariants

Review decisions identify the exact plan version

A composite foreign key prevents a review from pointing to a version owned by another plan.

100%

Review audit

plan_reviews references a plan, exact version, lead user, decision, comment, and timestamp. The composite foreign key enforces that the version belongs to that plan.

Workflow guards

Only declared transitions are valid. Returned plans need an edit that creates a new Draft version before resubmission. Published plans are terminal.

Database checks

Foreign keys bind actors, targets, chunks, versions, and reviews. Unique indexes enforce identities, per-release locators, source links, and plan version numbers.

Enums: roles; plan status; review decisions; curriculum level/node/target kinds; design origin/status; source type, authority, revision status, link role, and link status.
Source of truth: Drizzle database schema and shared JSON contracts. See workflow invariants.
