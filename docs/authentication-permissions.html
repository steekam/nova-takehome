Authentication and permissions

Follow a sign-in, then follow a protected request. The browser holds a session cookie; the API rebuilds the caller’s identity and checks each permission at the route and resource boundary.

1 · Who is calling?Authenticate the session cookie and load the active account.
2 · What capability?Evaluate the route’s declared policy against the principal.
3 · Which record?Check ownership, visibility, and workflow state in the service.

Public means “skip session authentication,” not “skip authorization.” A public route such as login still declares @Can(RoutePolicy, 'publicRoute'). The policy guard denies any HTTP route that has no policy declaration.
Why both a guard and a service check? The route guard knows the caller and the declared route ability. A service must load the plan or source to know its owner and workflow state, then pass that resource into a policy. This is where the API applies record-level rules.

02

Sign in creates a browser session

The API returns the principal as JSON and sends the secret token only in a cookie.

  1. Browser
    1 →POST /api/auth/login with email and password; the fetch client includes cookies.
  2. API route
    2 →Login route is throttled. @Public skips the session guard; @Can(publicRoute) permits the route. Nest’s global ValidationPipe validates the login DTO before the controller runs.
  3. AuthService
    3 →Find account; verify scrypt password; reject inactive or invalid account with the same 401 message. Unknown emails still perform dummy hash work.
  4. Session store
    4 →Generate 32 random bytes. Store the SHA-256 digest as session ID, plus user, family, expiry, and activity timestamps.
  5. API response
    5 ←Set HttpOnly; SameSite=Lax; Path=/ cookie. Return { user: principal }; never return the raw token in JSON.
  6. Web app
    6 ←Cache the principal for rendering and route selection. The browser attaches the cookie to later API calls.

What is stored

users
  id · email · passwordHash · role · isActive

auth_sessions
  id = SHA256(raw cookie token)
  familyId · isCurrent · userId
  createdAt · expiresAt · lastActiveAt

The key boundary

The cookie token is an unguessable credential. The database stores only its digest, so a read-only database leak does not reveal a value that can be replayed as the cookie.

On each request, the API resolves the session to the current active user and current role. The session does not freeze permissions at sign-in.

03

Session lifecycle and expiry

The session row records server-side state; the browser cookie is only the credential used to find it.

Absolute life12 hours from sign-in. Rotation keeps the original expiry.
Idle lifeOne hour since activity. A request after that revokes the session.
Activity writelastActiveAt updates no more than once per minute.
Current sessionOnly rows with isCurrent=true authenticate.
Sign out

Revoke one family

POST /api/auth/logout deletes sessions in the presented token family and clears the cookie. It remains public so an expired browser can clear its cookie.

Sign out everywhere

Delete account sessions

POST /api/auth/logout-all requires authentication, then deletes every session row for the current user.

Rotate

Retire the old token

POST /api/auth/rotate atomically retires the current row and inserts a new digest in the same family. The web app has no automatic caller today.

Account changes take effect quickly. Every authenticated request reloads the active flag and role from users. Deactivating an account blocks its next request; changing its role changes its next principal.

05

Capabilities do not decide record access by themselves

LessonPlanPolicy checks both the capability and facts about the requested plan. The service repeats record-specific checks after loading the record.

View

Owner, published, or submitted

A teacher can view their own plan at any state. Anyone with view permission can see a published plan. A curriculum lead can see a submitted plan. Drafts and returned plans stay private to their teacher.

Edit / submit / delete

Own plan plus valid state

The teacher capability is necessary, and teacherId must match the principal subject. State transitions and review history add further constraints.

Review

Lead capability plus transition

The lead needs lesson_plan:review. The service checks whether the submitted plan can be returned or published; publishing also reruns deterministic QA.

What happens when a request fails

1 · Session?Cookie missing, invalid, expired, or inactive account → stop.
2 · Route capability?Principal lacks the declared ability → stop.
3 · Record and state?Wrong owner or hidden state → deny; invalid transition → conflict.

06

The web app reflects permissions; the API enforces them

The client improves navigation and avoids offering actions that will fail. A caller can still bypass the UI, so the API repeats every security decision.

Web app · experience

  • currentUserQuery calls /api/auth/me.
  • TanStack route guards redirect anonymous users to sign in, and users without a capability to their role home.
  • App navigation uses lesson_plan:review to choose teacher or lead routes.
  • Plan responses include viewer.availableActions for buttons and links.
  • A 401 clears cached user data and returns the browser to sign-in.
↔

API · authority

  • AuthGuard validates the cookie against current database state.
  • PolicyGuard evaluates @Can before controller code runs.
  • Service-level authorize() checks resource ownership and write conditions.
  • Repositories only run after the use case passes those checks.
  • Mutations recheck against the locked/current row inside a transaction.
availableActions is presentation metadata. It helps decide which UI controls to render. It is computed server-side from permissions and state, but it is not a credential. Every endpoint still checks its policy even if the UI showed a button a moment ago.

✓

Keep these invariants in mind

These are the design checks that make the wiring understandable and dependable.

  • The browser never reads or stores the session token in JavaScript.
  • A principal is rebuilt from the active account and current database role.
  • Every HTTP route declares a policy; startup auditing catches omissions.
  • Route capability and record ownership/state are separate checks.
  • UI guards and availableActions improve UX; only API checks authorize.
  • Public routes are explicit and throttling still applies unless skipped.
  • Login failures use a generic credential error; unknown emails do dummy hash work.
  • Cookie-based writes pass the configured-origin and browser-origin checks.
